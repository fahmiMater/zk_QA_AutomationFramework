# Extract UI Elements

Write all user-facing explanations in Arabic. Keep identifiers, paths, commands, attribute names and code unchanged. Preserve observed names as rendered; never translate a name that may be used as evidence. Read [the CSV contract](resources/inventory-contract.md) before producing output.

The [synthetic example CSV](resources/example.ui-elements.csv) demonstrates the format only; never copy its IDs or rows into a real inventory. Its fallback rows show the governed pattern: testable now, debt tracked, upgrade to `data-automation-id` planned.

## 1. Establish the evidence and boundaries

- Identify the feature, screen, locale, and states needed by its acceptance criteria. Prefer a rendered DOM with browser accessibility evidence in an approved QA environment. If given HTML only, mark it `static-dom`; do not claim live visibility, computed accessibility, working actions, or overlays absent from the snapshot. A screenshot is visual evidence only: record visible names with `screenshot` evidence and `unverified` locator status; never infer DOM attributes from it.
- Use authorized, test-only sessions and reversible observation (open/close, expand, switch tabs or pages when appropriate). Do not submit, save, delete, upload, or change persistent data. If opening a control could mutate data, stop at that boundary and report the uncovered state. Never collect credentials, tokens, personal data, full row contents, raw DOM dumps, or sensitive URLs. Redact business record keys if necessary and do not treat redacted values as usable selectors.
- Read `framework/core/automation/AutomationAttribute.ts`, `framework/core/automation/Automation.ts` (its `byRole/byField/byColumn/byGrid/byDialog/byTab/byAction` builders are the contract-supported fallbacks above `visible-text`), `framework/core/factory/ComponentFactory.ts`, `docs/standards/LOCATOR_STRATEGY.md` and the relevant component implementation. Prefer observed `data-automation-id`; capture other contract attributes separately. Record `data-testid` as evidence, not as an automatic fallback. Do not invent IDs or override repository locator policy.

## 2. Walk all relevant levels, not only elements with IDs

- Enumerate semantic/native controls, assertion targets, and component boundaries. Recursively inspect test-relevant descendants until leaf controls, including controls inside cells and nested dialogs. Do not export decorative wrappers unless needed to scope the control. Record actual scope and the logical parent; a popup attached to `body` still belongs to the component that opened it. Correlate overlays with observed `aria-controls`, other verified DOM relationships, or an observed activation transition. Mark uncertainty when multiple overlays match. Record iframe and open Shadow DOM boundaries; report inaccessible frames or closed roots as gaps rather than guessing.
- **Grid/Table:** capture root, toolbar actions, header and column keys, sort/filter controls, header/row checkboxes, representative rows and cells, nested cell actions/editors, pagination controls, and applicable loading, empty, error, or expanded states. Record row identity, column identity and target match count in scope. Sample each relevant row/control variant and first/next or virtualized states when authorized. Do not enumerate an unbounded dataset or use row position as stable identity. Sampled records do not prove coverage of unrendered rows.
- **DatePicker:** capture wrapper, input, trigger, overlay, heading, month/year navigation/selectors, day grid and representative day variants (available, selected, disabled, out-of-month), clear/apply controls if present. Capture input constraints, date format and its evidence, locale and range selection where observed. Inspect closed and open states and both boundaries if safely reachable. Record actual `-input` / `-trigger` IDs separately from expected naming. The current `DatePickerComponent.selectDate()` uses text to pick a day: do not claim it verifies exact month/year or safe uniqueness without independent checks.
- **Other composites:** inspect all in-scope states of tabs, dropdowns, lookups and dialogs. Capture toggles, panel, options, search, alerts and confirmation controls with separate rows. Record which action exposes a lazy element. Reset observation state when safe. Mark states not available or not explored; no assertion of complete screen coverage unless bounded and verified.

## 3. Write the handoff and verify it

1. Write `<feature>.ui-elements.csv` in `apps/<app>/data/ui-inventory/` when the app already exists, otherwise in the user's designated output folder. Do not scaffold the app or change `framework/` as part of inventory. One row per element in an observed state, with referential `element_key` and `parent_key`. Use `coverage_gap` rows for inaccessible or unvisited in-scope states, with a reason. Keep machine headers and enum values exactly as specified in the contract.
2. Populate each property in its own column. Keep UI label and computed accessible name separate; record confidence and evidence type per row. A missing or non-unique `data-automation-id` never blocks, defers or disables a test: set `locator_status=fallback` (or `missing-id` when no strategy applies yet), pick the highest verified strategy from the hierarchy `automation-id → role+accessible-name → label → name-attr → html-id → visible-text → scoped-css` (positional XPath and generated/dynamic classes are forbidden), and record locator debt in `locator_strategy, fallback_reason, stability_risk, owner, remediation_ticket, review_by`. Empty/unverified values are not false. Do not propose a production locator where evidence is missing; propose the safest strategy the evidence supports.
3. Reparse the CSV with a CSV parser. Check the exact header, column counts, key uniqueness, parent references, allowed enums, and that `verified` locators have exactly one live match in the documented scope/state. Confirm that the composite controls are exploded into separate rows, no synthetic data is mixed into actual rows, and no secrets or sensitive field values were written. If checks were not run, state that explicitly.
4. Also write or update the locator-debt register (`locator-debt-register.csv` beside the inventory) listing every `fallback` row with its owner, ticket and date, and tag the affected tests `@fallback-locator` so they stay running and reportable. Summarize in Arabic: artifact path, source and states observed, elements with missing or ambiguous IDs, gaps with owners or the next evidence needed, and the locator-debt count with its upgrade path to `data-automation-id`. Hand off the CSV to `audit-ids`, `generate-page-object`, and `write-ui-test`. Do not infer acceptance criteria from the inventory or claim a test has run.
