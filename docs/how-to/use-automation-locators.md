# كيفية استخدام معرفات الأتمتة (Automation Locators)

للحفاظ على اختبارات قوية ومرنة وقابلة للاستدامة، فإن الإطار الخاص بنا **يمنع بشكل قاطع الاعتماد على النصوص الظاهرة (Visible Text)**، الكلاسات العشوائية (CSS Classes)، أو مسارات XPath المعقدة للوصول إلى عناصر واجهة المستخدم.

بدلاً من ذلك، نستخدم استراتيجية **Semantic ID Resolution**، وتحديداً الخاصية `data-automation-id`. يوضح هذا الدليل كيفية استخدامها.

## لماذا `data-automation-id`؟
- **مقاومة تغييرات التصميم والتوطين:** إذا تغير لون الزر أو تم ترجمة نصه من "حفظ" إلى "Save"، فلن تفشل الاختبارات!
- **صيانة أسهل:** يسهل على المطورين وضع هذا المعرّف (Attribute) لضمان عدم تأثر الأتمتة عند تعديل الشاشات.

## الطريقة الصحيحة للوصول للعناصر

لنفترض أن لديك زر الحفظ التالي في الكود المصدري (HTML):
```html
<button class="btn-primary" data-automation-id="dialog-save-btn">حفظ البيانات</button>
```

في اختبارك (أو في المكون Component)، **لا يجب** أن تفعل هذا:
```typescript
// ❌ خطأ - يعتمد على نص قابل للتغيير أو الترجمة
await page.locator('text=حفظ البيانات').click();

// ❌ خطأ - يعتمد على كلاس قد يتغير للتصميم
await page.locator('.btn-primary').click();
```

**✅ الطريقة الصحيحة:**
يجب استخدام معرّف الأتمتة الخاص بنا:
```typescript
// ✅ صحيح - قوي ولا يتأثر بالتغييرات الظاهرية
await page.locator('[data-automation-id="dialog-save-btn"]').click();
```

*(تلميح: المكونات Core Components الموجودة في `framework` تحتوي مسبقاً على دوال تعتمد بشكل كامل على هذه المعرفات ولا تتطلب منك كتابة Locators يدوياً في كل مرة).*

## قاعدة الأولوية في الـ Selectors (كما هو محدد في CODING_STANDARDS)
إذا كنت بصدد كتابة Locator لعنصر جديد ولا يتوفر له `data-automation-id` بعد (يُفضل أن تطلب من مطور الواجهات إضافته)، التزم بترتيب الأولوية التالي:
1. `data-automation-id` (المفضل دائماً).
2. خصائص إمكانية الوصول (Accessibility attributes مثل `aria-label`).
3. خصائص HTML الثابتة (Stable HTML attributes مثل `name` في النماذج).
